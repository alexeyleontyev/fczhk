# ФКЖК — MVP 3

Telegram-бот и Mini App для организации пятничного футбола. MVP 1: регистрация, отдельные очереди полевых/вратарей, подтверждение оплаты, финализация, гости, резерв, замены, ручное распределение и публикация команд. MVP 2: оценки игроков с историей, временные рейтинги на матч и до трех разных сбалансированных вариантов команд. Все административные операции доступны в мобильном интерфейсе.

Python управляется через **uv**; точные зависимости зафиксированы в `uv.lock`. Frontend: React + TypeScript + Vite, зависимости в `frontend/package-lock.json`. Рабочая БД — PostgreSQL; SQLite используется только в локальном демо и быстрых тестах.

## Локальное демо без Telegram

Требуются Python 3.12 (uv может установить его), uv и Node.js 22.

```sh
uv sync
npm --prefix frontend ci
npm --prefix frontend run build
uv run fczhk demo
```

Открыть **http://127.0.0.1:8000**. На экране входа выбрать администратора или игрока. Добавленные данные сохраняются в `.local/demo.db`; повторный запуск не сбрасывает их. Сервер демо слушает только loopback. Публикации имитируются локальным worker и явно помечаются «Демо»; в Telegram ничего не отправляется.

Демо содержит вымышленные имена, манеж, стоимость и реквизиты. Оно не использует реальный токен из `.env` и не предназначено для публичного размещения.

Демо не придумывает оценки от имени игроков: новые карточки появляются без рейтинга. В разделе «Игроки» можно оценить конкретного зарегистрированного участника или пройти список кнопкой «Оценить игроков». Администратор задает гостям и участникам без оценок временные значения в блоке «Рейтинги на эту игру». После финализации доступен блок «Подобрать команды». Ссылкой `http://127.0.0.1:8000/?game=<ID>` можно открыть конкретную игру.

При первом запуске этой ветки существующая демо-БД дополняется новыми таблицами; прежние данные не удаляются. Это специальный режим демо. Для рабочей PostgreSQL обязательна миграция, описанная ниже.

Для разработки интерфейса запустить дополнительно:

```sh
npm --prefix frontend run dev
```

Vite откроет адрес http://127.0.0.1:5173 и направит `/api` на backend :8000. При изменении backend перезапустить `uv run fczhk demo`.

## Реальное подключение Telegram

1. Создать бота в BotFather. Получить токен и добавить бота администратором в разрешенный чат/канал: это нужно для надежной проверки членства. В месте публикаций выдать права публикации/редактирования сообщений бота.
2. Создать локальный `.env` по `.env.example`. Указать токен, числовые Telegram ID администраторов, чат сообщества, чат публикаций, username бота, публичный HTTPS-адрес и PostgreSQL URL. `.env` игнорируется Git.
3. В BotFather настроить Main Mini App на тот же HTTPS-адрес: кнопки постов используют прямые ссылки `https://t.me/<bot>?startapp=game_<id>`.
4. Применить миграции, запустить API и worker.
5. Выполнить `uv run fczhk configure-bot`. Эта явная команда изменяет меню, список команд и режим доставки обновлений вашего бота. Если задан `FCZHK_WEBHOOK_SECRET`, настраивается webhook; иначе webhook удаляется без потери ожидающих обновлений и нужен отдельный `uv run fczhk bot`.
6. В Mini App войти администратором, настроить место, время, стоимость, реквизиты и включить еженедельный шаблон. По умолчанию расписание выключено и реальные реквизиты не заполнены.

Подключение к настоящему Telegram и отправка реального поста не выполнялись при разработке: токен, чат и домен не предоставлены. Проверка Mini App внутри Telegram на реальных iOS/Android и один пробный сбор являются приемкой развертывания.

### Запуск сервисов без Docker

```sh
uv run fczhk migrate
uv run fczhk serve
# В другом процессе:
uv run fczhk worker
# Только если выбран polling:
uv run fczhk bot
```

### PostgreSQL для локальных интеграционных проверок

```sh
docker compose up -d db
```

Для чистого окружения без `.env`: пользователь/БД `fczhk`, локальный пароль `local-development-only`, адрес `127.0.0.1:55432`. Этот пароль только для локальной разработки. Если `.env` задает `POSTGRES_PASSWORD`, используйте его. Docker volume сохраняется при остановке контейнера.

### Развертывание Docker + HTTPS

В `.env` обязательны настоящий пароль `POSTGRES_PASSWORD`, домен `DOMAIN`, а также `FCZHK_DATABASE_URL=postgresql+psycopg://fczhk:<URL-encoded-password>@db:5432/fczhk`. Для контейнеров база находится на `db:5432`, а не на localhost. Остальные значения Telegram задаются как выше.

```sh
docker compose --profile production up -d --build
docker compose exec app uv run --frozen --no-dev fczhk configure-bot
# Только для polling, когда WEBHOOK_SECRET пуст:
docker compose --profile polling up -d bot
```

DNS домена должен указывать на сервер, порты 80/443 — быть доступны Caddy. Не запускать polling и webhook одновременно. API проверяет настройки и отказывается запускаться в production без Telegram, администраторов, HTTPS и PostgreSQL.

API запускает миграции перед приемом трафика. Worker начинает работу после готовности API. `/api/health` проверяет соединение с БД. Docker перезапускает сервисы после сбоя. Не менять первоначальный пароль работающего volume через `.env` без отдельного изменения учетной записи PostgreSQL.

## Проверки

```sh
uv run ruff check src tests migrations
uv run pytest -q
npm --prefix frontend run build
```

Дополнительные тесты PostgreSQL пропускаются без явного URL. Они применяют настоящие миграции и проверяют одновременное расписание, повторную запись, конфликт финализации, одновременное изменение одной оценки и обновление базы MVP 1 с сохранением данных. Для каждого теста создается отдельная случайная схема; только она удаляется после проверки.

```sh
FCZHK_TEST_DATABASE_URL=postgresql+psycopg://fczhk:local-development-only@127.0.0.1:55432/fczhk uv run pytest tests/test_postgres.py -q
```

Браузерные проверки используют работающее локальное демо на :8000:

```sh
cd frontend
npx playwright install chromium
npm run test:e2e
```

Браузерные сценарии добавляют отдельные тестовые игры с будущими датами, гостей и оценки демонстрационных аккаунтов в демо-БД. Скриншоты и трассировки сохраняются в `frontend/test-results/` и не коммитятся. Не запускать эти тесты против реальной базы.

Проверка времени подбора на пяти воспроизводимых синтетических наборах, без БД:

```sh
uv run python scripts/benchmark_balance.py
```

Если среда ограничивает домашний кэш uv, локальные команды можно запускать как `uv --cache-dir .cache/uv run --no-sync ...` после `uv sync`.

## Доставка постов

Открытие сбора сохраняет игру и задание публикации одной транзакцией. Worker отправляет пост отдельно. После утверждения команд администратор нажимает «Опубликовать составы». Ошибка Telegram не отменяет утвержденные данные.

При определенном отказе Telegram отображается ошибка и доступен повтор. При сетевой неопределенности или перезапуске посреди отправки автоматический повтор запрещен: администратор проверяет чат и явно запускает повтор, чтобы не создавать незаметные дубли. Для больших сообщений сохраняются ID уже доставленных частей.

Изменение участников сбрасывает распределение и утверждение, старые посты помечаются неактуальными. Если Telegram не дает отредактировать старое сообщение, интерфейс сообщает об этом; администратор уведомляет чат и публикует новую версию.

## Резервное копирование

```sh
sh scripts/backup.sh /absolute/path/to/independent-backups
```

Скрипт создает новый архив `pg_dump -Fc` и проверяет его оглавление через `pg_restore`. Копировать архивы на отдельное хранилище; расписание и срок хранения задает владелец сервера. Сам скрипт не удаляет старые резервные копии.

Проверку полного восстановления проводить в отдельной пустой БД, не поверх рабочей:

```sh
docker compose exec db createdb -U fczhk fczhk_restore_check
docker compose exec -T db pg_restore -U fczhk -d fczhk_restore_check --exit-on-error < /absolute/path/to/backup.dump
docker compose exec db psql -U fczhk -d fczhk_restore_check -c 'SELECT count(*) FROM matches;'
```

Проверка оглавления не заменяет пробное восстановление. Для повторных проверок использовать новое имя пустой БД; сценарий не содержит автоматического удаления базы.

## Обновление MVP 1 → MVP 2

1. Сделать резервную копию PostgreSQL и проверить восстановление в отдельной БД.
2. Остановить старые API/worker/bot на время обновления; не запускать две версии приложения поверх одной БД.
3. Обновить зависимости: `uv sync --locked`, `npm --prefix frontend ci`, `npm --prefix frontend run build`.
4. С настроенным `.env` выполнить `uv run fczhk migrate`. Миграция `c2a486fe91d0` добавляет семь таблиц и служебную строку, не меняя игроков, заявки, оплаты и старые снимки составов. Повторное применение безопасно.
5. Запустить API/worker/bot. При использовании Docker заново собрать образы; команда app выполняет миграции при старте.

Для уже утвержденных в MVP 1 команд не подставляются сегодняшние рейтинги задним числом: показывается отсутствие снимка. Новые утверждения сохраняют рейтинги и параметры подбора. Для отката предпочтительно восстановление предварительной копии: `alembic downgrade` удаляет новые таблицы с оценками и расчетами.

## Границы MVP 2

Результаты/голы и статистика относятся к MVP 3, аукцион — к MVP 4. Онлайн-оплаты не подключены: подтверждение перевода остается ручным.

Допуски балансировки и округление порога разнообразия при недоборе имеют предварительные значения, доступные администратору в настройках расчета. Для выпуска на реальных игроках их нужно подобрать совместно с организатором. Полный перебор гарантирует минимальный дисбаланс, но эвристика выбора разных вариантов не гарантирует глобальный максимум разнообразия. Если подходящих вариантов найдено меньше трех, приложение показывает причину и оставляет ручной режим.

## MVP 3: результаты

После начала утвержденной игры администратору доступен блок «Результат матча»: фактические участники, голы, передачи, автоголы и неизвестные авторы. Сохраните черновик либо завершите матч. Исправления обновляют статистику; профили и архив содержат ссылки на результаты. Подробности: [решения MVP 3](docs/MVP3_IMPLEMENTATION.md).
