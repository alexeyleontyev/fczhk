# Игровой рейтинг: реализация и варианты развития

[Оглавление](README.md) · [Архитектура](ARCHITECTURE.md). Статистические выводы относятся только к исходной выборке; обновление документации не означает повторного эксперимента на новых данных.

Статус: эксперимент, актуализировано 17.10.2026; результаты сравнения ниже получены 26.09.2026. История игр загружена в локальную demo.db; подробности и ограничения указаны в [документе импорта](HISTORICAL_RESULTS_IMPORT.md). Рейтинг можно посмотреть в разделе «Игроки» и явно выбрать как экспериментальный способ подбора; по умолчанию остаются оценки сообщества.

## Первый расчёт на истории

Добавлен [пересчёт OpenSkill](../src/fczhk/game_ratings.py) по датам завершённых матчей. Для первой версии выбрана `ThurstoneMostellerFull` с `margin=0`: исход матча — победа, поражение или ничья. Учитываются только полевые игроки; вратарские роли и заглушки не смешиваются с ними. Хранящаяся в базе история остаётся источником истины: исправление результата меняет рейтинг при следующем чтении. Рейтинг сообщества не изменяется. На исходном импорте список показывал 54 полевых игрока, их `mu`, `sigma` и число игр; порядок задан осторожной оценкой `mu − 3σ`, а не одной `mu`. Для просмотра она переведена в шкалу `round(1500 + 10 × (mu − 3σ))`: новичок начинает с 1500, а расчёт модели и подбор команд по `mu` не меняются.

В разделе подбора команд администратор может выбрать «OpenSkill · эксперимент». Алгоритм [точно перебирает разбиения](../src/fczhk/game_balancing.py) полевых, минимизируя разницу суммарных `mu` команд; разницу нормирует на среднюю численность для настройки допуска. Он предлагает до трёх разных составов и сохраняет снимок использованных `mu`, `sigma`, историю игр и параметры в `balance_runs`. Если состав или предшествующий результат изменится, прежний расчёт помечается устаревшим и не применяется. Вратари распределяются вручную. Для игрока без истории используются исходные `mu=25`, `sigma=25/3`; его неопределённость показывается в деталях расчёта.

OpenSkill **может** учитывать разницу мячей: при `rate(teams, scores=[...])` и положительном `margin` разница влияет на величину обновления. При `margin=0` счёт задаёт только порядок команд. В установленной версии 6.2.0 коэффициент зависит от `log1p(|разница| / margin)` после порога `margin`; поэтому его нельзя трактовать как прямую прибавку очков за каждый гол. См. [руководство](https://openskill.me/en/stable/manual.html) и [FAQ](https://github.com/vivekjoshy/openskill.py/blob/main/docs/source/faq.rst).

Хронологическая проверка на 17 матчах: перед каждой игрой рассчитана вероятность победы белых только по более ранним играм, затем обновлены оценки. Ниже средний квадрат ошибки этой вероятности; ничья условно имеет целевое значение 0,5. Это сравнительная метрика для режимов, а не полноценная оценка вероятности ничьей.

| `margin` | Все 17 игр | Только 15 без ничьих |
| ---: | ---: | ---: |
| 0 | 0,2755 | 0,3031 |
| 1 | 0,2749 | 0,3022 |
| 2 | 0,2760 | 0,3034 |
| 3 | 0,2756 | 0,3033 |
| Всегда 50/50 | 0,2206 | 0,2500 |

Дополнительная проверка включает вратарей как участников команд с **отдельными рейтингами для полевой и вратарской ролей**. Согласованные заглушки участвуют с исходной неопределённой оценкой только в своей игре; их не связывают с конкретными игроками. Из 17 игр в 11 указаны вратари обеих сторон, но в трёх из этих игр есть заглушки; в шести играх вратари не указаны.

| `margin` | Только полевые | Полевые и вратари |
| ---: | ---: | ---: |
| 0 | 0,2755 | 0,2742 |
| 1 | 0,2749 | 0,2735 |
| 2 | 0,2760 | 0,2747 |
| 3 | 0,2756 | 0,2744 |
| Всегда 50/50 | 0,2206 | 0,2206 |

На восьми играх с двумя известными вратарями результат обратный: при `margin=0` ошибка выросла с 0,3061 до 0,3087. Значит, маленькое улучшение на полном наборе нельзя считать доказательством пользы учёта вратарей. Оба режима всё ещё хуже ориентира 50/50 на этой выборке. В действующем экспериментальном подборе остаются только полевые; включение вратарей можно повторно оценить после накопления истории.

Разница между вариантами OpenSkill также слишком мала для вывода о пользе разницы мячей. 17 игр недостаточно для надёжной настройки модели. Поэтому просмотр рейтинга и отдельный способ подбора помечены как эксперимент; организатор сам выбирает этот режим, а по умолчанию используется прежний способ. Проверку можно повторить командой:

```sh
FCZHK_DATABASE_URL=sqlite:///./.local/demo.db uv run python scripts/evaluate_game_ratings.py
```

## Задача

Добавить рейтинг по результатам матчей как **отдельный способ подбора составов**. Он не заменяет действующие оценки сообщества: средние атаки и защиты полевых и защиты вратарей используются в текущем подборе, а для новых игроков служат исходным ориентиром. Рейтинг команды как постоянной сущности не нужен: составы меняются каждую неделю, поэтому храним оценку каждого игрока и обновляем её по фактическим составам завершённого матча.

Один общий результат игры даёт мало сведений о каждом из 16–18 участников. Перемешивание составов помогает различать их вклад со временем, но частые совместные выступления одних и тех же людей и малое число матчей оставляют высокую неопределённость. Её следует хранить и показывать, а не скрывать за одним баллом.

## Сравнение

| Вариант | Возможности и цена выбора |
| --- | --- |
| Командный Elo или Glicko | Простая контрольная модель. Нужно самостоятельно определить сумму сил, обновление каждого участника, ничьи и неопределённость; для задачи с меняющимися большими командами это существенная часть работы. |
| TrueSkill | Непосредственно моделирует игроков в командах, их неопределённость и ничьи; у Python-библиотеки есть `quality` для оценки пары составов. Параметр частоты ничьих можно подбирать по истории. При возможном коммерческом использовании нужно отдельно проверить условия использования названия и модели, указанные в лицензии Python-проекта. |
| OpenSkill, `PlackettLuce` | Универсальная модель, которую документация библиотеки рекомендует для большинства случаев. Поддерживает команды, равные места, разную численность, параметры динамики и неопределённость. Кандидат для сравнения на истории. |
| OpenSkill, `ThurstoneMostellerFull` | Модель с явным порогом ничьей `epsilon`. Подходит как первый кандидат для двух футбольных команд; это гипотеза для проверки на наших матчах, а не доказанное превосходство над `PlackettLuce` или TrueSkill. |
| TrueSkill 2 | Использует дополнительные индивидуальные сигналы. Голы и передачи здесь не описывают вклад защитников и вратарей сопоставимо с атакующими, поэтому на первом этапе не нужен. |

Текущий эксперимент использует **OpenSkill `ThurstoneMostellerFull`**. `PlackettLuce` остаётся кандидатом для дальнейшего сравнения, а метод сообщества — рабочим вариантом по умолчанию. Разница скорости вычисления при нашем объёме не является решающим фактором.

## Правила и дальнейшее развитие

1. Источник `mu` (ожидаемой силы) и `sigma` (неопределённости) — история завершённых матчей. Она загружается за четыре пакетных запроса; в процессе хранится до 32 кешированных пересчётов по содержимому истории и параметрам модели. Изменение результата, участников, амплуа или связи карточек меняет ключ. Возвращается копия результата, а снимок расчёта состава сохраняется отдельно. При росте истории измерять время и память заново. Полевую и вратарскую роли не смешивать: вратарей пока назначают вручную.
2. Обновлять оценки только из завершённых игр по **фактическим** участникам и победе, поражению или ничьей. Не приравнивать результат одной команды к восьми независимым победам над каждым игроком другой команды.
3. Сначала игнорировать разницу мячей и личные голы/передачи при обновлении рейтинга. Минуты участия можно учесть позднее, если их начнут достоверно фиксировать. Отдельно измерить, улучшает ли использование счёта прогноз на истории.
4. Для экспериментальной балансировки сравнивать суммы ожидаемой силы `mu` команд с учётом численности. Не подставлять `mu − 3·sigma` вместо силы новичка: это осторожная оценка для списка игроков, а не ожидаемый вклад в матч. Показывать `sigma` и предлагать до трёх разных составов.
5. Для игрока без матчей использовать исходные `mu=25`, `sigma=25/3`. Шкалу оценок сообщества пока не переносить в OpenSkill: способ такого переноса надо проверить отдельно. Метод сообщества остаётся выбором по умолчанию.
6. Сохранять снимок использованных рейтингов, истории и параметров при расчёте состава. Утверждённый состав не менять задним числом. После исправления исторического результата новый расчёт пересобирает последовательность рейтингов; старый вариант состава становится устаревшим и не применяется.

## Проверки перед снятием экспериментального статуса

Проиграть импортированные игры в хронологическом порядке: перед каждой игрой прогнозировать её исход только по более ранним играм. Проверять качество прогнозов победы/поражения и ничьих раздельно, а также калибровку вероятностей. `predict_win` OpenSkill не следует без проверки трактовать как полную вероятность трёх исходов: документация предупреждает, что с версии 6 суммы вероятностей места и ничьей не образуют единицу. Сравнить с текущими оценками при одинаковых составах и отдельно оценить, насколько разные предложенные разбиения удовлетворяют ограничениям. При малой истории оставлять рейтинг предварительным.
