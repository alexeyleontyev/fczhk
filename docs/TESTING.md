# Проверки и границы приёмки

[Оглавление](README.md) · [Архитектура](ARCHITECTURE.md) · [Выпуск](DEPLOYMENT_PLAN.md).

Нужны Python 3.12, uv, Node.js 22; для интеграционных проверок — Docker, PostgreSQL 17, Bash и ShellCheck. Установить зависимости из lock-файлов:

```sh
uv sync --locked
npm --prefix frontend ci
uv run ruff check src tests migrations scripts
uv run pytest -q
npm --prefix frontend run build
shellcheck deploy/lib.sh scripts/*.sh
git diff --check
```

Без `FCZHK_TEST_DATABASE_URL` PostgreSQL-сценарии пропускаются. SQLite не проверяет поведение блокировок PostgreSQL. Для полного набора указать тестовую БД; каждый тест создаёт случайную схему и удаляет только её:

```sh
docker compose up -d db
FCZHK_TEST_DATABASE_URL=postgresql+psycopg://fczhk:local-development-only@127.0.0.1:55432/fczhk uv run pytest -q
```

Пример пароля подходит только к новой локальной БД без собственного `.env`. Для существующего volume использовать его реальные учётные данные. Не направлять тесты на production.

## Браузер и образ

После сборки frontend:

```sh
cd frontend
npx playwright install chromium
npm run test:e2e
```

Playwright запускает отдельный сервер на `127.0.0.1:8001` с временной SQLite. Существующий сервер на этом порту не переиспользуется; `.local/demo.db` не меняется. Все действия выполняются в тестовой БД. Сценарии прогнозов дожидаются настоящего времени начала тестовой игры. Трассировки и скриншоты сохраняются в `frontend/test-results/`, не включаются в Git. Telegram Login и внешняя доставка в этих тестах имитируются.

Из корня репозитория:

```sh
docker build -t fczhk:local .
bash scripts/smoke-image.sh fczhk:local
```

Smoke создаёт собственные сеть и контейнеры, применяет миграции дважды, проверяет импортёры и карты имён, frontend, API, worker/readiness, dump и полный restore в изолированный PostgreSQL. Завершение API и worker по SIGTERM проверяется по exit code 0. Временные ресурсы удаляются; чужие контейнеры и volume не затрагиваются. Для restore нужен запас RAM под tmpfs.

Ограничение числа запросов списка архива сохранено.

Браузерные сценарии дополнительно покрывают истечение сессии, выход, устаревший initData, страницы архива и действия администратора с телефона.

Последующий CI выявил гонку ставок SQLite-демо. Добавлен регрессионный тест: второй капитан ждёт фиксации первой транзакции, затем лот разрешается один раз с правильным бюджетом. Перед исправлением тест воспроизводит ошибку. SQLite теперь резервирует запись до чтения; PostgreSQL по-прежнему проверяется отдельно. При подсчёте запросов архива команды начала транзакции исключены, ограничение числа запросов данных сохранено.

Проверка образа также выявила преждевременный restore во временный PostgreSQL инициализации. Регрессия выпуска имитирует готовый Unix socket при недоступном TCP: восстановление и миграции не должны начаться, последний успешный образ сохраняется. Реальные smoke/restore используют TCP readiness и явный отказ по тайм-ауту.

В [CI](../.github/workflows/checks.yml) тесты выполняются на push и pull request. После успеха собирается и проверяется образ; публикация в GHCR выполняется только на push в ветку по умолчанию. Тег — полный Git SHA; существующий тег не перезаписывается. Проверенный digest выводится в summary job. Для нового выпуска проверять именно run нужного SHA.

## Производительность и внешняя приёмка

```sh
uv run python scripts/benchmark_balance.py
```

Команда измеряет подбор на воспроизводимых синтетических наборах без БД. Регрессии запросов архива и истории рейтинга проверяются Python-тестами. Эти проверки не заменяют нагрузочный замер на выбранном production-сервере и рабочем объёме истории.

Перед включением расписания выполнить Telegram-пилот на реальных iOS/Android и в браузере: доступ участника и отказ постороннему, запись, оплата, составы, прогноз, публикация и пометка старого поста. Проверить внешние тревоги и восстановление копии с независимого хранилища. Реальные отправки, доступность внешнего backup и целевые RPO/RTO не подтверждаются локальными тестами.

Проверки обновления Google-данных покрывают неизвестного автора автогола, подтверждённую передачу после смены команды, сохранение старых ID и запрет переноса исключения на другое событие. Уникальность имени проверяется через API и непосредственно БД; повторные имена Telegram не блокируют вход и не захватывают гостя. PostgreSQL проверяет новую миграцию, сохранение данных и отказ отката при неизвестных авторах; Playwright сохраняет автогол без автора.

Ролевая модель проверяется в `tests/test_administrators.py`: защита владельца, запрет самоназначения и управления ролями обычным администратором, отсутствие Telegram ID в доступных ему административных ответах, назначение/отзыв для уже выданной сессии, сохранение после нового запуска API, аудит и приоритет явного отзыва над legacy-списком. PostgreSQL проверяет миграцию `a71f4b6d2e90`, совпадение с ORM, отказ потери решений при downgrade и конкурентные изменения прав с одной ревизией. Браузерный сценарий `administrators.spec.ts` назначает и снимает администратора через панель владельца, проверяет его интерфейс в отдельной сессии и отсутствие горизонтального переполнения на телефоне.

В сценарии истечения сессии отзыв выполняется при запросе явного обновления игры. Так проверяется настоящий ответ 401 и возврат на вход без гонки между фоновым опросом и кликом по уже исчезнувшей кнопке. Повторения используют отдельные даты тестовых игр.

Отдельный браузерный тест задерживает ответ текущей игры при входе, открывает список игроков и проверяет, что поздний ответ не сбрасывает выбранную вкладку. Начальная вкладка задаётся до загрузки профиля; дальнейший выбор пользователя сохраняется. Настройки и смена роли явно недоступны до завершения текущей операции, чтобы клики по ним не терялись; после загрузки тест открывает настройки.

Сезоны проверяются в `tests/test_seasons.py`: отсутствие смешивания исходов, личных показателей, партнёров, архива и пользовательских прогнозов; общая сумма, пустой сезон, права доступа и московский год по умолчанию. OpenSkill при любом выборе сезона возвращает один и тот же общий рейтинг и число игр, включая запрос с неизвестной меткой. `tests/test_game_ratings.py` проверяет хронологический расчёт по нескольким сезонам при обратном порядке импорта, перенос рейтинга между сезонами, отсутствие будущих результатов в прогнозе и использование старого сезона в подборе. PostgreSQL проверяет миграцию `f97c3e8d210a`, сохранение матчей, совпадение ORM и отказ потери сезона при downgrade. Импортные тесты покрывают зеркальное расположение команд старой таблицы, амплуа, исходные ячейки, явные годы, пропуск только подтверждённых турниров, повторное использование связанного alias после переименования и атомарный отказ повторной записи. Playwright `seasons.spec.ts` проверяет общий выбор периода между зачётами, карточкой игрока, архивом и прогнозами и независимость OpenSkill от этого выбора.

Фильтр периода по умолчанию проверяется в Playwright: текущий московский год выбирается при наличии более позднего сезона, тот же период виден в карточке игрока; доступны прошлый сезон и общая история. Общая история сохраняется при переходе в профиль; после выхода и нового входа восстанавливается текущий сезон. Проверяются также граница московского года и отсутствие текущей метки. Сценарий результата MVP 3 явно выбирает сезон своей исторической тестовой игры.

Тактическая доска проверяется в `tests/test_lineups.py`: доступ участника к чтению и предварительному подбору, отсутствие записей при примерке, серверный запрет подтверждения обычным игроком, атомарный отказ при неполных и неверных назначениях или координатах, конфликт изменившихся оценок и фиксация снимка. Для старых игр проверяются имена после привязки профиля, стабильность команд, амплуа и координат, приоритет сохранённых оценок (включая нулевые) и использование текущих оценок при отсутствии снимка, отдельно для полевых и вратарей. Исторические записи при чтении не переписываются. Браузерный `lineups.spec.ts` дополнительно проверяет прочерки при отсутствии обоих источников, сохранённые нули и неполную сумму. Аукционный тест проверяет отсутствие закрытых ставок в ответе доски и запрет обхода активных/приостановленных торгов. PostgreSQL дополнительно проверяет одновременное подтверждение одной версии: один успех, один конфликт, один снимок.

Браузерный `lineups.spec.ts` проверяет схему 3–3–1 и игрока с минимальной суммой А+З в углу каждой половины при 18 участниках, перенос из списка, изменение команды при пересечении центра, перемещение стрелками, размещение касанием на телефоне, неизменность общих команд при личных действиях, сохранение черновика, разделение пользователей и конфликт после утверждения другим администратором. `tactical-layout.spec.ts` отдельно проверяет выбор самого слабого полевого без участия вратаря, неизвестные и нулевые оценки, устойчивость при равенстве оценок и изменении порядка ответа, небольшие команды и лишних полевых. `mvp1.spec.ts` и `mvp2.spec.ts` проходят фиксацию через кнопку «Зафиксировать составы на игру». `mvp2.spec.ts` также проверяет переключение вариантов без записи расчётов, компактные эффективные оценки, восстановление личного варианта, утверждение снимка и очистку личной доски без сброса общего состава. `mvp4.spec.ts` сохраняет проверки закрытых ставок, ничьих, раскрытия цен и истории и переходит к подтверждению через тактическую доску.

## Планируемые уведомления

`tests/test_notifications.py` проверяет границу анонса, отсутствие ранней игры, пропуски и ручные черновики, истечение сообщения, сохранение backoff при повторном tick, независимые переключатели, права администратора, повторную запись и отмену, время напоминания и серверные данные отсчёта. `tests/test_auctions.py` проверяет отдельный чат, выключение сообщений без остановки торгов и остатки бюджетов после разрешения лота. `tests/test_telegram.py` проверяет отмену своей заявки и защиту от повторного callback после новой записи.

Проверки команд бота в `tests/test_telegram.py` выполняются с подменённым Bot API без реальных сообщений: отсутствие `/players` в обработчиках, справке и меню, отдельный `/profile` с общей статистикой и текущим сезоном, история привязанного игрока, пустая статистика, смена года по Москве и отказ доступа до регистрации или чтения профиля.

PostgreSQL проверяет одновременные анонсы четырёх worker-транзакций, миграцию `0b7c6d9e214f` поверх прежней схемы с сохранением игр и публикаций, повторный upgrade и запрет потери настроек при downgrade. `frontend/e2e/notifications.spec.ts` проверяет сохранение чекбоксов, размеры 320/390/1440 px и отсчёт при ошибочных часах устройства с обновлением игры на нуле. `browser-login.spec.ts` дополнительно проверяет сохранение действующей сессии после временной ошибки загрузки профиля; ошибку 401 по-прежнему обрабатывает общий API-клиент.

## Telegram-идентификатор профиля

`tests/test_telegram_identity.py`, `test_browser_auth.py` и `test_telegram.py` проверяют обновление никнейма из подписанного Mini App initData, OIDC claim `preferred_username` и Telegram-сообщений, удаление никнейма с возвратом к ID, сохранение alias и сессий при входе, переименовании и привязке истории. Никнейм не редактируется через API имени; общий каталог не содержит Telegram-реквизиты. PostgreSQL проверяет миграцию `1c8d7e0f325a` поверх прежней схемы, сохранение аккаунта и сессии, совпадение ORM, повторный upgrade, защиту downgrade и обратный переход при пустых никнеймах. Playwright `telegram-identity.spec.ts` проверяет одну строку идентификации в собственном профиле и статистике игрока, ссылку на Telegram, fallback на ID и отсутствие переполнения при ширине 320 px.

Браузерная авторизация дополнительно проверяется с реальным форматом Telegram OIDC `id`: числом и десятичной строкой, включая большие ID, повторный вход в существующую карточку и права владельца. Отклоняются boolean, дроби, отрицательные и слишком большие ID, пробелы, знак, ведущие нули, Unicode-цифры и экспоненциальная запись. Все варианты проходят штатную проверку подписи, issuer, audience, срока и nonce. Тест журнала отказов проверяет отсутствие токенов, cookie, nonce и личных данных при регистрации этапа и типа ошибки.
