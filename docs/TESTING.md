# Проверки и границы приёмки

[Оглавление](README.md) · [Архитектура](ARCHITECTURE.md) · [Выпуск](DEPLOYMENT_PLAN.md).

Нужны Python 3.12, uv, Node.js 22; для интеграционных проверок — Docker, PostgreSQL 17, Bash и ShellCheck. Установить зависимости из lock-файлов:

```sh
uv sync --locked
npm --prefix frontend ci
uv run ruff check src tests migrations scripts
uv run pytest -q
npm --prefix frontend run build
shellcheck deploy/lib.sh scripts/*.sh
git diff --check
```

Без `FCZHK_TEST_DATABASE_URL` PostgreSQL-сценарии пропускаются. SQLite не проверяет поведение блокировок PostgreSQL. Для полного набора указать тестовую БД; каждый тест создаёт случайную схему и удаляет только её:

```sh
docker compose up -d db
FCZHK_TEST_DATABASE_URL=postgresql+psycopg://fczhk:local-development-only@127.0.0.1:55432/fczhk uv run pytest -q
```

Пример пароля подходит только к новой локальной БД без собственного `.env`. Для существующего volume использовать его реальные учётные данные. Не направлять тесты на production.

## Браузер и образ

После сборки frontend:

```sh
cd frontend
npx playwright install chromium
npm run test:e2e
```

Playwright запускает отдельный сервер на `127.0.0.1:8001` с временной SQLite. Существующий сервер на этом порту не переиспользуется; `.local/demo.db` не меняется. Все действия выполняются в тестовой БД. Сценарии прогнозов дожидаются настоящего времени начала тестовой игры. Трассировки и скриншоты сохраняются в `frontend/test-results/`, не включаются в Git. Telegram Login и внешняя доставка в этих тестах имитируются.

Из корня репозитория:

```sh
docker build -t fczhk:local .
bash scripts/smoke-image.sh fczhk:local
```

Smoke создаёт собственные сеть и контейнеры, применяет миграции дважды, проверяет импортёры и карты имён, frontend, API, worker/readiness, dump и полный restore в изолированный PostgreSQL. Завершение API и worker по SIGTERM проверяется по exit code 0. Временные ресурсы удаляются; чужие контейнеры и volume не затрагиваются. Для restore нужен запас RAM под tmpfs.

## Покрытие и последний контроль

18.10.2026 для разделения сезонов локально прошли **204 обычных Python-теста и 19 PostgreSQL-сценариев**, **24 Playwright-сценария**, Ruff и сборка TypeScript/Vite. Импортная проверка текущего старого XLSX разобрала 46 обычных игр и 552 гола без нерешённых замечаний; 13 турниров исключены явно. Проверка CI и образа относится к конкретному SHA выпуска.

17.10.2026 перед слиянием изменений выполнены **165 Python-тестов**, включая **12 PostgreSQL-сценариев** и **5 проверок безопасности скриптов выпуска**, и **18 Playwright-сценариев**. Также прошли Ruff, TypeScript/Vite, ShellCheck, проверка Compose, сборка и smoke образа с восстановлением копии. CI merge-коммита `2bfd58f` завершился успешно: [GitHub Actions](https://github.com/alexeyleontyev/fczhk/actions/runs/39025636378). Это датированный результат, не фиксированное ожидаемое количество тестов навсегда.

Проверяются очереди и оплаты, конфликтующие транзакции, миграции с сохранением данных, сессии и авторизация, оценки и снимки, результаты и статистика, секретность аукциона, дедлайны прогнозов, отмена игры, пропуск недели, связь профилей, сбои доставки и безопасное поведение deploy/rollback. Браузерные сценарии дополнительно покрывают истечение сессии, выход, устаревший initData, страницы архива и действия администратора с телефона.

Последующий CI выявил гонку ставок SQLite-демо. Добавлен регрессионный тест: второй капитан ждёт фиксации первой транзакции, затем лот разрешается один раз с правильным бюджетом. Перед исправлением тест воспроизводит ошибку. SQLite теперь резервирует запись до чтения; PostgreSQL по-прежнему проверяется отдельно. При подсчёте запросов архива команды начала транзакции исключены, ограничение числа запросов данных сохранено.

Проверка образа также выявила преждевременный restore во временный PostgreSQL инициализации. Регрессия выпуска имитирует готовый Unix socket при недоступном TCP: восстановление и миграции не должны начаться, последний успешный образ сохраняется. Реальные smoke/restore используют TCP readiness и явный отказ по тайм-ауту.

В [CI](../.github/workflows/checks.yml) тесты выполняются на push и pull request. После успеха собирается и проверяется образ; публикация в GHCR выполняется только на push в ветку по умолчанию. Тег — полный Git SHA; существующий тег не перезаписывается. Проверенный digest выводится в summary job. Для нового выпуска проверять именно run нужного SHA.

## Производительность и внешняя приёмка

```sh
uv run python scripts/benchmark_balance.py
```

Команда измеряет подбор на воспроизводимых синтетических наборах без БД. Регрессии запросов архива и истории рейтинга проверяются Python-тестами. Эти проверки не заменяют нагрузочный замер на выбранном production-сервере и рабочем объёме истории.

Перед включением расписания выполнить Telegram-пилот на реальных iOS/Android и в браузере: доступ участника и отказ постороннему, запись, оплата, составы, прогноз, публикация и пометка старого поста. Проверить внешние тревоги и восстановление копии с независимого хранилища. Реальные отправки, доступность внешнего backup и целевые RPO/RTO не подтверждаются локальными тестами.

Проверки обновления Google-данных покрывают неизвестного автора автогола, подтверждённую передачу после смены команды, сохранение старых ID и запрет переноса исключения на другое событие. Уникальность имени проверяется через API и непосредственно БД; повторные имена Telegram не блокируют вход и не захватывают гостя. PostgreSQL проверяет новую миграцию, сохранение данных и отказ отката при неизвестных авторах; Playwright сохраняет автогол без автора.

Ролевая модель проверяется в `tests/test_administrators.py`: защита владельца, запрет самоназначения и управления ролями обычным администратором, отсутствие Telegram ID в доступных ему административных ответах, назначение/отзыв для уже выданной сессии, сохранение после нового запуска API, аудит и приоритет явного отзыва над legacy-списком. PostgreSQL проверяет миграцию `a71f4b6d2e90`, совпадение с ORM, отказ потери решений при downgrade и конкурентные изменения прав с одной ревизией. Браузерный сценарий `administrators.spec.ts` назначает и снимает администратора через панель владельца, проверяет его интерфейс в отдельной сессии и отсутствие горизонтального переполнения на телефоне.

В сценарии истечения сессии отзыв выполняется при запросе явного обновления игры. Так проверяется настоящий ответ 401 и возврат на вход без гонки между фоновым опросом и кликом по уже исчезнувшей кнопке. Повторения используют отдельные даты тестовых игр.

Отдельный браузерный тест задерживает ответ текущей игры при входе, открывает список игроков и проверяет, что поздний ответ не сбрасывает выбранную вкладку. Начальная вкладка задаётся до загрузки профиля; дальнейший выбор пользователя сохраняется. Настройки и смена роли явно недоступны до завершения текущей операции, чтобы клики по ним не терялись; после загрузки тест открывает настройки.

Сезоны проверяются в `tests/test_seasons.py`: отсутствие смешивания исходов, личных показателей, партнёров, архива, OpenSkill и прогнозов; общая сумма, пустой сезон, права доступа и московский год по умолчанию. PostgreSQL проверяет миграцию `f97c3e8d210a`, сохранение матчей, совпадение ORM и отказ потери сезона при downgrade. Импортные тесты покрывают зеркальное расположение команд старой таблицы, амплуа, исходные ячейки, явные годы, пропуск только подтверждённых турниров, повторное использование связанного alias после переименования и атомарный отказ повторной записи. Playwright `seasons.spec.ts` проверяет общий выбор периода между зачётами, карточкой игрока, архивом и прогнозами.

Фильтр периода по умолчанию проверяется в Playwright: текущий московский год выбирается при наличии более позднего сезона, тот же период виден в карточке игрока; доступны прошлый сезон и общая история. Общая история сохраняется при переходе в профиль; после выхода и нового входа восстанавливается текущий сезон. Проверяются также граница московского года и отсутствие текущей метки. Сценарий результата MVP 3 явно выбирает сезон своей исторической тестовой игры.

В мобильном сценарии подбора `mvp2.spec.ts` проверяется компактная строка рейтинга: временная оценка скрывает оценку сообщества; при отсутствии временной остаётся одна строка сообщества без подписи о незаданной оценке. После проверки выполняются выбор варианта, ручные изменения и утверждение составов.
