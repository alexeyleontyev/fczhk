# HTTP API

Состояние кода: 25.10.2026. [Оглавление](README.md) · [Настройки](CONFIGURATION.md) · [Архитектура](ARCHITECTURE.md).

Все пути начинаются с `/api`. JSON-запросы используют `Content-Type: application/json`. В demo/test доступны `/api/docs` и `/api/openapi.json`; в production они отключены. Точные поля и ограничения входных моделей — в [schemas.py](../src/fczhk/schemas.py), ответы и проверки прав — в соответствующих [маршрутах](../src/fczhk/routes).

## Общие правила

- Доступ «участник» требует `Authorization: Bearer <session_token>` и членства в сообществе. «Администратор» проверяет актуальные права из БД либо роль владельца; legacy-список используется только до явного решения владельца. «Владелец» сверяет Telegram ID с `FCZHK_OWNER_ID` (при его отсутствии — с первым `FCZHK_ADMIN_IDS`). Черновики игр скрыты от обычного участника.
- Telegram-вход возвращает `token` и `player`. Проверенный OIDC claim `id` допускает положительное целое число либо строку из ASCII-цифр без знака и ведущих нулей; сервер приводит его к целому числу в диапазоне Telegram ID. Поле `sub` не используется как ID Bot API. Причина отказа пишется в журнал только как этап проверки и класс ошибки, без JWT, cookie, claims и текста исключения. Браузерный вход сначала получает challenge с cookie, затем передаёт `id_token`; сервер проверяет origin, nonce, подпись, срок и членство. Logout отзывает только переданную сессию. Demo login существует только в demo и доступен с loopback.
- Изменения игры используют актуальную `version`, оценки/прогнозы и управление аукционом — свои ревизии согласно модели. После конфликта версии 409 загрузить данные заново; не повторять изменение автоматически поверх чужой версии. Имя игрока уникально: создание гостя или переименование в занятое имя также возвращает 409, в этом случае нужно выбрать другое имя.
- Время — ISO 8601 с часовым поясом. Дата пропуска — `YYYY-MM-DD`, дата не раньше сегодняшней по Москве без созданной игры. Амплуа: `field` / `keeper`, команды: `white` / `black`.
- Прикладные ошибки возвращают `{"detail":"сообщение"}`; валидация 422 может содержать массив подробностей. 401 — нет действующей сессии, 403 — запрет доступа, 404 — нет доступного ресурса, 409 — конфликт состояния/версии, 429 — лимит входа (`Retry-After: 60`), 503 — недоступность БД либо degraded readiness. Ошибки правил могут иметь код 400. Ответы `/api` не кешируются браузером.

Оценивать через GET/PUT ratings можно любую действующую карточку каталога, независимо от наличия Telegram у оцениваемого. Автор должен войти в приложение; самооценка запрещена. После связывания исторической карточки оценки доступны через итоговую карточку; среднее учитывает последнюю оценку автора один раз.

`GET /api/players/{id}/reviews` возвращает текущие оценки с именами авторов, сгруппированные по `field`/`keeper`. В каждой записи: `author_id`, `author`, `attack`, `defense`, `at`. История изменения чужих оценок доступна только администратору через прежний ratings endpoint. В профиле оценки по авторам закрыты спойлером и запрашиваются при его открытии. В чужом профиле кнопка «Оценить игрока» открывает форму оценки выбранного игрока; закрытие формы возвращает в профиль. В своём профиле действие скрыто. Рядом с общей статистикой показаны до пяти последних исходов выбранного периода слева направо от старой игры к новой: победа зелёным, ничья жёлтым, поражение красным. Кружочков столько же, сколько сыгранных матчей, без пустых мест; при отсутствии игр блок скрыт. В каталоге чекбокс скрывает игроков без оценок в обоих амплуа; настоящие нулевые оценки считаются оценками.

`ArchiveDetailsEdit`: обязательные `version`, `game_day` (`YYYY-MM-DD`), `start_time` (`HH:MM` по Москве либо `null`), `location` (до 200 символов, пустая строка означает неизвестное место) и `season` (1–40 символов). Метод предназначен для завершённых и отменённых игр. Занятая дата или устаревшая версия возвращает `409`; завершённую игру нельзя перенести в будущее. Пустое время сохраняет технический timestamp при неизменной дате, но помечает время как неизвестное. Изменение даты без времени использует техническую московскую полночь. Повторное сохранение тех же значений не создаёт ревизию.

Коррекция сохраняет участников, результат, прогнозы, снимки оценок и исходный импорт; создаёт аудит со старыми/новыми значениями. Старые публикации составов, результата и личных вариантов помечаются устаревшими, ожидающие отправки отменяются. Новое сообщение автоматически не отправляется. Ответы полной игры и списка содержат `time_known`; `historical` по-прежнему обозначает происхождение из импорта. История содержит `actor` — действующий alias автора либо `null` для системы — наряду с `actor_id`, `action`, `data` и `at`.

### Автоматический подбор

Экран тактической доски использует следующие методы:

| Метод | Путь | Доступ | Тело |
| --- | --- | --- | --- |
| GET | `/api/matches/{match_id}/lineup` | Участник | — |
| POST | `/api/matches/{match_id}/lineup/preview` | Участник | `version`, `method: community \| game` |
| POST | `/api/matches/{match_id}/lineup/confirm` | Администратор | LineupConfirm |
| POST | `/api/matches/{match_id}/lineup/share` | Участник | LineupShare |

`lineup` возвращает версии игры и списка, `fingerprint`, выбранных игроков с эффективными оценками, назначения, координаты `placements` и утверждённый снимок `official_players`, если он существует. Завершённые игры содержат фактических участников с `editable: false`: `registration_id` равен отрицательному ID исходного участника, а `player_id` и `alias` разрешаются в действующий профиль после привязки. Ключи назначений и координат остаются стабильными. Приоритет оценок для фактического амплуа: сохранённые на игру (`source: snapshot`), иначе текущие оценки сообщества (`community`); при отсутствии обоих источников — `null` и `missing`. Сохранённый ноль считается оценкой. `auction` содержит только публичные назначения и цены, без закрытых ставок. Черновики игр скрыты от обычных участников.

`preview` возвращает те же данные и `result.variants`; вратари предварительно распределяются по одному на сторону. Метод не меняет базу и доступен также при открытом сборе по предварительному списку. Настройки расчёта фиксированы; результаты кэшируются с ограничением размера. Отсутствие оценок блокирует метод `community`, но не `game`.

`LineupConfirm`: `version`, `roster_version`, `fingerprint`, полный объект `assignments: {registration_id: white | black | null}`, необязательный `placements: {registration_id: {x, y}}`, `source: manual | community | game | auction` и `variant: 0..2`. Координаты нормированы в диапазоне `[0, 1]`, белые занимают нижнюю половину (`y >= 0.5`), чёрные — верхнюю. Координаты допустимы только для назначенных участников соответствующей команды. Версии, актуальность оценок, права и допустимость составов проверяются до атомарного подтверждения; конфликт возвращает `409`. Публикация не запускается автоматически. Подробнее: [тактическая доска](TACTICAL_LINEUPS.md).

`lineup.share_available` показывает, настроен ли расширенный чат. `LineupShare`: `version`, `roster_version`, `fingerprint`, полный объект `assignments` с распределением всех игроков по обеим командам и необязательный `official: true` для оценок из `official_players` (по умолчанию используются `players`). Сервер определяет автора по сессии и формирует текст с составами и суммами; ID чата, текст и автора клиент не задаёт. Ответ — `{publication_id, status}`, обычно `pending`: сообщение ставится в очередь, общие команды и версия игры не меняются. Пустые/неполные команды отклоняются (`400`), чужие ID, устаревшие данные и отсутствие чата — `409`; повтор запроса идемпотентен. Между разными вариантами одного автора требуется минута (`429`). Метод доступен для открытой, зафиксированной, утверждённой и завершённой игры.

Прежние административные методы сохранены для совместимости:

| Метод | Путь | Доступ | Тело |
| --- | --- | --- | --- |
| PUT | `/api/matches/{match_id}/registrations/{reg_id}/rating` | Администратор | MatchRatingEdit |
| GET | `/api/balance/settings` | Администратор | — |
| POST | `/api/matches/{match_id}/balance` | Администратор | BalanceGenerate |
| GET | `/api/matches/{match_id}/balance` | Администратор | — |
| POST | `/api/matches/{match_id}/balance/{run_id}/apply` | Администратор | BalanceApply |

В `BalanceRun.inputs` поля `community` и `temporary` содержат отдельные пары `attack`/`defense` либо `null`; `attack`, `defense` и `source` по-прежнему указывают используемый расчетом рейтинг. Это снимок значений на момент расчета.

Состояние аукциона содержит `prices`: объект `{registration_id: amount}` для выигранных и автоматически распределенных игроков. Капитаны отсутствуют в `prices`, бесплатные назначения имеют 0. Суммы нерешенного лота не раскрываются. Открытие каждого лота, включая первый и повторные круги, создаёт `auction_open`: номер, круг, игрок, текущие команды с капитанами, ценами, заполненностью полевых мест и назначенными вратарями, а также остатки бюджетов. После второй ставки создается одна публикация `auction_lot`; при равенстве обе ставки раскрываются, бюджет не списывается и игрок уходит на следующий круг. Сообщение результата включает команды после назначения победителю. Автоматическое бесплатное завершение создает отдельные сообщения о назначениях с ценой 0 и составами после каждого назначения. Адресат всех аукционных сообщений — `extended_chat_id`, чекбокс — `extended_auction_enabled`. Неподанные и закрытые ставки не попадают в сообщения открытия лотов или составы; повтор запросов не создаёт дублей.

Успешный старт аукциона в той же транзакции создаёт `auction_start` с упоминаниями обоих капитанов по Telegram ID. Новый аукцион получает отдельное уведомление; повтор запроса со старой версией отклоняется без дубликата. Worker отправляет только этот вид публикаций в HTML; пользовательские имена экранируются.

Сохранение результата с `completed=true` создаёт публикацию `result`: фактические команды и вратари, счёт и исход, авторы каждого гола и передачи, отдельные пометки автоголов и неизвестных авторов. Черновики не публикуются. Изменение завершённого результата создаёт исправленный итог и делает прежнюю публикацию неактуальной; ожидающая отправки прежняя версия отменяется. Сохранение того же результата и повтор запроса не создают новое сообщение. Длинные итоги разбиваются на части с учётом UTF-16, без разметки.

`GET /api/matches/{match_id}` возвращает `team_ratings.strength`: `total` (полная сумма или `null` при пропусках), `rated_total` (сумма известных оценок), `rated`, `count` и `teams.white/black` с теми же четырьмя полями. Суммируются исходные эффективные А+З полевых и З вратарей, без нормировки автоподбора и без резерва. Данные фиксируются в снимке при утверждении и включаются в пост со стартовыми составами. Старые снимки без силы сбора не дополняются сегодняшними оценками.

### Оплаты и новый конкурс прогнозов

`PaymentReport` принимает `{"reported":true}` или `false` только для собственной активной заявки в открытой, финализированной или утверждённой игре. Повтор того же состояния не меняет версию. Подтверждённую администратором оплату участник менять не может. Административный `Payment` по-прежнему принимает `version` и `paid`, дополнительно — необязательный `reported` для исправления отметки игрока.

В интерфейсе две отдельные отметки: `payment_reported` — «Оплачен / Не оплачен» от игрока, `paid` — «Подтверждено / Не подтверждено» от администратора. Положительные значения зелёные, отрицательные красные. Администратор исправляет их отдельными кнопками; изменение одной отметки сохраняет другую.

Списки участников и резерва находятся в «Обзоре». Отдельные вкладки «Участники» и «Управление» удалены; панель административных действий расположена вверху обзора, журнал публикаций раскрывается там же. Кнопка «Добавить игрока» находится в заголовке блока «Участники». Под именем каждого участника отдельной строкой показаны дата и время записи по Москве, без спойлера и повторяющегося статуса всего сбора. Ширина обеих отметок оплаты фиксирована по строке «Не подтверждено» и не меняется при переключении.

В списке регистраций добавлены `payment_reported`, `payment_status` (`unpaid`/`reported`/`confirmed`) и `in_main`. До финализации основной список определяется временем записи с лимитами 16 полевых и 2 вратаря; резерв выводится отдельно. `selected` и финализация по-прежнему учитывают только подтверждённую оплату, с сохранением административно закреплённых мест. Отмена и повторная запись сбрасывают обе отметки оплаты. Кнопка «Я оплатил» в `/game` использует тот же сервис отметки, без административного подтверждения.

`PredictionEdit` принимает либо `white_score` и `black_score`, либо `category` из `Б4`, `Б13`, `Н`, `Ч13`, `Ч4`, вместе с `revision` и `approved_version`. При передаче обоих вариантов категория должна соответствовать счёту. Категории означают разницу от 4 мячей, от 1 до 3 или ничью. Матрица начисления (строка — прогноз, столбец — итог):

| Прогноз / итог | Б4 | Б13 | Н | Ч13 | Ч4 |
| --- | --- | --- | --- | --- | --- |
| Б4 | 3 | 1 | 0 | 0 | 0 |
| Б13 | 0,5 | 2 | 0,5 | 0 | 0 |
| Н | 0 | 0,5 | 3 | 0,5 | 0 |
| Ч13 | 0 | 0 | 0,5 | 2 | 0,5 |

Миграция `5b4d82a731cf` сохраняет стартовую «Сумму» сезона 2026 из [исходного листа](https://docs.google.com/spreadsheets/d/1A9zju1qrvvLqfUXAx1E3hYplLoQ6iLNYLa-vMNOq58A/edit?gid=1925724999): 28 участников, 91 очко, снимок на 25.10.2026. Доли хранятся целыми половинками. Старые прогнозы остаются в истории, получают `scoring_version=1` и исключаются из нового рейтинга; новые и заново подтверждённые прогнозы имеют версию 2. Повторная миграция не начисляет стартовые очки ещё раз. `baseline_points` в зачёте показывает стартовую часть; `two_points` и `half_points` дополняют счётчики начислений. Результат берётся из завершённого матча; исправления пересчитывают новые очки без накопления дублей.

Форма прогноза видна сверху после финализации, ввод разрешается после утверждения команд и строго до старта. Пост составов содержит «Сделать прогноз» со ссылкой `startapp=game_{id}_prediction`; в браузере эквивалент — `/?game={id}&screen=prediction`. Быстрый ввод счёта в редакторе результата создаёт настоящие строки голов с неизвестными авторами. Заполненные авторы, передачи и автоголы сохраняются; уменьшение счёта ниже количества заполненных событий отклоняется в форме.

## Форматы чтения и важные операции

`GET /api/me`, ответы успешного входа и `GET /api/players/{player_id}/stats` содержат `telegram_id` и `telegram_username` (nullable). В профиле интерфейс показывает одну строку: ссылку `@username`, а при отсутствии никнейма — `Telegram ID: …`; у гостя строка скрыта. Никнейм обновляется из проверенного Mini App initData, подписанного OIDC claim `preferred_username` или Telegram-сообщения боту. Удалённый никнейм очищается при следующем входе/обращении к боту. Ранее привязанные аккаунты без сохранённого никнейма показывают ID до такого обновления. Переименование alias и объединение с историей сохраняют Telegram-привязку. Через `PATCH /api/me` эти поля изменить нельзя. Общий список `/api/players` не включает Telegram-реквизиты; просмотр профиля требует действующей сессии участника.

Четыре исторические заглушки вратарей возвращаются в `/api/players` одной карточкой с `shared_keeper: true` и alias «Приглашённый вратарь». У неё нет персональных оценок или статистики (`400`), привязка к Telegram-профилю недоступна. Из личных зачётов и списка партнёров заглушки исключены. В результатах и тактических составах общая подпись используется при сохранении отдельных исходных ID участников обеих команд. Подробнее: [импорт истории](HISTORICAL_RESULTS_IMPORT.md).

`GET /api/matches?limit=20&offset=0` возвращает массив кратких карточек, без общего `total` и без полных заявок/составов. `limit` от 1 до 100, `offset` от 0; порядок — начало и ID по убыванию. Карточка содержит `id`, `starts_at`, `game_day`, `season`, `location`, `historical`, `status`, `version`, `participant_count`, `result` (null либо `completed` и `score.white/black`). Клиент загружает следующую страницу; пустая страница означает конец.

`GET /api/matches/current` возвращает полную ближайшую будущую неотменённую игру, иначе последнюю неотменённую, либо null. Администратору доступны также черновики. `GET /api/matches/{match_id}` — полная карточка выбранной игры. Получение архива больше не заменяет получение полной карточки: клиентам прежнего API необходимо использовать detail endpoint.

`POST /api/matches/{match_id}/actions/{action}` поддерживает `open`, `finalize`, `approve`, `publish`, тело `{"version":7}`. Версию брать из последнего ответа, а не из примера. Публикация ставится в очередь; успешный HTTP-ответ не означает доставку в Telegram.

Кнопка «Утвердить составы» в открытом сборе вызывает подтверждение `finalize`. Перед отправкой интерфейс сравнивает `in_main` с серверным `selected` и по именам показывает, кто не войдёт в сбор и кто перейдёт из резерва, отдельно для полевых и вратарей. Отметки игрока «Оплачен» недостаточно: требуется подтверждение администратора; закреплённые места сохраняются. При недоборе показывается фактическая численность. «Да» отправляет запрос с показанной версией, «Нет» возвращает к обзору без изменений. Конфликт версии не утверждает сбор автоматически: данные обновляются для повторного решения администратора.

Отмена: `POST /api/matches/{match_id}/cancel`, например `{"version":7,"reason":"Манеж закрыт"}`. Только до начала и без результата; причина 2–300 символов. Сохраняются заявки, оплаты и аудит; активный аукцион прекращает принимать ставки, прогнозы закрываются. Уведомление отправляется для уже открытого сбора, отмена черновика не публикуется.

Пропуск даты: `POST /api/schedule/skipped` с `{"game_day":"2026-10-23","reason":"Манеж закрыт"}`. Подходит любой день недели не раньше сегодняшнего по Москве. Если игра уже создана, нужна отмена игры. Пропуск блокирует автоматическое и ручное создание и перенос на эту дату. DELETE снимает исключение; расписание снова может создать игру в своём окне. Список возвращает последние 100 исключений.

`GET /api/template` и `PUT /api/template` доступны администратору. В `TemplateEdit` обязательны `version`, `enabled`, `opening_weekday`, `opening_time`, `game_weekday`, `start_time`, `location`; остальные поля сохраняют прежние значения по умолчанию. Нумерация дней: понедельник `0` … воскресенье `6`; часы — `HH:MM`, по Москве. В один день `opening_time` должно быть строго раньше `start_time`, иначе 422. Устаревшая `version` даёт 409. После GET передавать в PUT актуальные поля целиком, чтобы не потерять настройки. Изменения применяются к следующим создаваемым играм без перезапуска worker.

Пример расписания: `opening_weekday=6`, `opening_time="23:45"`, `game_weekday=0`, `start_time="00:15"` — сбор открывается в воскресенье, игра начинается в ближайший понедельник через полчаса. Worker выбирает текущий период записи по московскому времени, в том числе через границу недели, месяца и года. После простоя догоняет открытие только до старта игры; повторный запуск не создаёт дубль. Пост `collection` содержит фактические `starts_at` и место созданного матча, а не дату открытия сбора.

Заявка на историю: `POST /api/me/profile-claim` с `{"guest_id":123}`. Решение администратора: `POST /api/profile-claims/{player_id}/resolve` с `{"guest_id":123,"accept":true}`. ID примеров заменять реальными. Подтверждение объединяет историю, отклоняет конкурирующие заявки и блокируется при конфликтующем участии в одной игре. Поиск по имени не подтверждает личность.

При подтверждении, в том числе через `POST /api/players/{guest_id}/link`, alias исторической карточки переносится в зарегистрированный профиль. ID зарегистрированного игрока и его сессии сохраняются. Скрытая исходная карточка получает уникальное служебное имя; исторические события продолжают ссылаться на её прежний ID, а чтение статистики разрешает его в активный профиль. Поле `guest` в ответе заявки показывает alias активного профиля после объединения. Аудит `guest.linked` сохраняет `guest_alias` и `previous_target_alias`. Отклонение заявки или конфликт участия оставляют оба имени без изменений. Повторный Telegram-вход не перезаписывает alias.

`GET /api/leaderboards` возвращает результаты и средние сообщества, `/api/game-ratings` — экспериментальный OpenSkill. Поиск и порог числа игр применяются frontend; это не query-параметры данных endpoints. Профиль возвращает историю/партнёров, интерфейс первоначально раскрывает пять игр и трёх партнёров.

## Управление администраторами

Только владелец имеет доступ к `GET /api/administrators` и `PUT /api/administrators/{player_id}`. Обычный администратор получает 403. GET возвращает активные карточки с Telegram ID: `id`, `alias`, `telegram_id`, `role` (`owner`, `admin`, `player`) и `revision`. Гостевые и объединённые карточки исключены. Общий список аккаунтов с ролями и Telegram ID доступен только владельцу; Telegram-реквизиты отдельного профиля доступны участникам через описанные выше маршруты.

PUT принимает `{"is_admin":true,"revision":0}` и возвращает обновлённую запись. Для отзыва передать `false`; ревизию брать из GET. Изменение защищено блокировкой строки; устаревшая ревизия даёт 409, отсутствующий игрок — 404, гостевая карточка и изменение владельца — 409. Дополнительные поля, попытка передать `is_owner` и некорректные типы отклоняются с 422. Повтор того же состояния с актуальной ревизией не создаёт лишнего события. Изменения записываются в аудит как `administrator.granted` и `administrator.revoked` с автором, целевым игроком, прежними и новыми правами.

## Служебный доступ

`/api/telegram/webhook` принимает `X-Telegram-Bot-Api-Secret-Token`, совпадающий с `FCZHK_WEBHOOK_SECRET`; пользовательская сессия не заменяет этот секрет. `/api/metrics` требует `Authorization: Bearer <FCZHK_METRICS_TOKEN>`; пустое значение отключает доступ (403). Это текст Prometheus, не JSON.

`/api/health` проверяет БД. `/api/health/ready` возвращает `status` и булев `worker`, с 503 при проблеме. Детальная очередь и ошибки доступны только администратору через `/api/operations`. Перед `/api/publications/{pub_id}/retry` для `uncertain` проверить чат: повтор может создать дубль. `/retry-stale` повторяет пометку старого доставленного поста. Оба действия журналируются.

`GoalEvent` с `kind="own_goal"` допускает `author_id=null`; `assist_id` всегда null. При известном авторе он должен быть участником противоположной команды. Ответ результата может содержать `assist_team_switches` — подтверждённые при импорте исключения смены команды (`goal_id`, `player_id`, `team`). Это данные ответа, не изменяемые поля запроса: исключение действует только для точного события, игрока и команды.

## Сезоны и период статистики

`GET /api/seasons` возвращает массив меток по убыванию, например `["2026","2024-2025"]`. Сезоны, представленные только административными черновиками, скрыты от обычного участника.

Необязательный query-параметр `season` (1–40 символов) поддерживают `/api/matches`, `/api/players/{id}/stats`, `/api/leaderboards` и `/api/predictions/standings`. Пример: `/api/leaderboards?season=2024-2025`. Отсутствие параметра означает общую статистику; неизвестная метка возвращает пустую выборку. Пустая строка отклоняется с 422. Фильтр архива применяется до `limit`/`offset`.

Интерфейс по умолчанию запрашивает текущий сезон (метка московского года, иначе последняя доступная), но отсутствие query-параметра в API сохраняет прежнюю семантику общей истории. Явный выбор «Общая · все сезоны» отправляет запрос без `season`.

В `/leaderboards` фильтруется только `results`; `community` содержит текущие общие оценки. `/api/game-ratings` всегда возвращает единый OpenSkill по всей истории в хронологическом порядке; `matches` и число игр каждого игрока также относятся ко всей истории. Прежний query-параметр `season` принят для совместимости, помечен устаревшим и не влияет на ответ, включая неизвестную метку. Интерфейс не передаёт его для OpenSkill. Партнёры, исходы и история в `/stats` относятся к одному выбранному периоду.

`GameFields`/`GameEdit` принимают `season`: строку 1–40 символов или null. При создании без метки используется год московской даты игры; при редактировании null/отсутствие сохраняет прежнюю метку, даже если дата меняется. Явная строка назначает новую метку. Detail и краткие карточки игр возвращают `season`. Миграция существующих игр задаёт `2026` независимо от их даты; старый импорт явно задаёт `2024-2025`.

## Уведомления и отсчёт до сбора

`GET /api/schedule/next` доступен авторизованным участникам. Возвращает `server_now`, `opening_at`, `starts_at`, `location`. Времена содержат часовой пояс; если автоматическое расписание выключено или доступного окна нет, последние три поля равны `null`. Пропущенные недели и даты с уже созданной игрой, включая ручной черновик, исключаются. Метод ничего не создаёт и не раскрывает ID чатов. До обработки открытия worker может вернуть уже наступивший `opening_at`: клиент показывает «Сбор открывается…» и обновляет игру, не разрешая запись самостоятельно.

Администратор настраивает уведомления через существующие `GET/PUT /api/template` с проверкой `version`:

| Поле | Значение |
| --- | --- |
| `announcements_chat_id` | Чат анонсов: отрицательный Telegram ID либо `@username`; по умолчанию пусто |
| `announcement_enabled` | Анонс перед автосбором; по умолчанию `false` |
| `announcement_minutes` | За сколько минут до открытия отправить анонс: 1–10080, по умолчанию 30 |
| `payment_reminder_enabled` | Одно напоминание об оплате на игру; по умолчанию `false` |
| `payment_reminder_weekday` / `payment_reminder_time` | День 0–6 и `HH:MM` по Москве; по умолчанию четверг, 18:00 |
| `extended_chat_id` | Отдельный чат подробных сообщений; по умолчанию пусто |
| `extended_auction_enabled` | Старт, открытие и результаты лотов аукциона, включая текущие команды и остатки баллов |
| `extended_registration_enabled` | Записи, смены амплуа и включение администратором |
| `extended_cancellation_enabled` | Отмены записей |

Три переключателя расширенного чата по умолчанию `true`, однако без `extended_chat_id` сообщения не создаются. Уведомления аукциона больше не используют `FCZHK_PUBLICATION_CHAT_ID`; основные публикации сбора, составов и итогов продолжают использовать его. Пустой чат анонсов запрещён при включённых анонсах или напоминаниях. Время напоминания должно быть между открытием сбора и началом игры в недельном расписании. Для существующих ручных игр напоминание рассчитывается по фактической дате начала; автоматическое открытие может быть выключено.

Публикации создаются в транзакции и отправляются worker. Повторный tick, одинаковая заявка или повторный callback не создают дубль. Анонс не отправляется после открытия; напоминание не отправляется после начала или отмены игры. Изменение настроек отменяет ожидающие анонсы; отключение типа расширенных сообщений отменяет его ожидающие и ошибочные публикации. Сообщения с неопределённой доставкой не пересылаются автоматически. `publications.match_id` и `operations.problems[].match_id/game_day` могут быть `null` для анонса, созданного до игры.

В `/game` бот предлагает «Записаться полевым», «Записаться вратарем», «Отменить запись». Callback отмены снимает только собственную заявку и защищён от повторного применения. После финализации самостоятельная отмена по-прежнему закрыта. Веб-приложение использует существующий `DELETE /api/matches/{id}/join`.
