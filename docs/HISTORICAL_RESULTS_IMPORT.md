Повторный запуск с `--replace-demo` снова заменит содержимое demo.db после резервной копии; без него пересекающиеся даты приводят к ошибке до записи. Для dry run:

```sh
uv run python scripts/import_history.py --xlsx .local/history-source-2026-09-26.xlsx
```

Импорт сохраняет итоговый счёт, фактические составы, голы, автоголы и передачи в `matches`, `match_results`, `result_participants`, `result_goals`. В `audit` для каждой игры лежат ID исходной таблицы, дата вкладки, SHA-256 XLSX, исходные ячейки A:G строк 1–51, текстовые примечания, исходные записи вратарей и строк голов. Оценки `DEF`/`AT` из старой таблицы сохранены только в исходных ячейках журнала; оценки сообщества [импортированы из другой таблицы](COMMUNITY_RATINGS_IMPORT.md).

Время начала и место исторических игр неизвестны. Для сортировки используется техническое время 12:00 МСК и техническое поле `location`; интерфейс показывает «Время и место неизвестны». Заявки, оплаты и публикации не выдумывались. Для входа в локальное демо роли администратора и игрока привязываются к двум импортированным полевым игрокам через условные Telegram ID 1001/1002. Эти связи нужны только локальному демо и не должны переноситься в PostgreSQL.

## Импорт в PostgreSQL

Скрипт принимает базу из `FCZHK_DATABASE_URL` и не зависит от SQLite, включён в Docker-образ вместе с картой поправок. История сезона 2026 уже находится в рабочей PostgreSQL; следующие команды предназначены для чистой базы или явно выбранных отсутствующих дат. Для чистой базы после миграций команда имеет вид:

```sh
FCZHK_DATABASE_URL=postgresql+psycopg://... uv run python scripts/import_history.py --xlsx .local/history-source-2026-09-26.xlsx --apply
```

Перед записью в рабочую базу нужно отдельно сопоставить исходные написания с существующими карточками игроков: одинаковый псевдоним не доказывает, что это один человек. Импортёр использует явные соответствия `aliases`, точные имена и подтверждённые цепочки связи карточек, включая сохранённый `guest_alias` из аудита. Несколько кандидатов одного имени блокируют импорт. Новые карточки создаются только для оставшихся имён. Проверка личности нужна до запуска; похожие имена автоматически не объединяются. Флаг `--replace-demo` для PostgreSQL заблокирован.

## Связь истории с Telegram

В production импорт создаёт исторические гостевые карточки без условных demo ID. Игрок выбирает карточку в своём профиле, администратор проверяет соответствие и принимает заявку. Исходные участия и снимки сохраняются; расчёты разрешают связь с текущим профилем. Если обе карточки участвовали в одной игре, сначала исправить протокол — автоматического слияния конфликтующих участий нет.

При любом повторном импорте сначала сравнить SHA исходника, выполнить dry run и проверить фактический состав нескольких игр. Для непустой базы ограничение сопоставления по alias выше остаётся действующим; заявка на профиль не устраняет коллизии на этапе импорта.

Для 09.10 исходная строка состава Сереги (белые, вратарь) сохранена. Его переход и передача за чёрных записаны отдельным подтверждённым исключением, видимым в протоколе и примечании матча. Текущая модель хранит одну основную команду на игрока/матч: исход и партнёры Сереги считаются по исходной строке белых; отдельного учёта двух таймов нет. Полевой OpenSkill этого вратаря не использует. Исключение относится только к данному событию и не разрешает произвольные передачи соперника в API.

Владелец подтвердил: ноябрь–декабрь в начале книги относятся к 2024 году, последующие январь–декабрь — к 2025. По его решению учитываются только обычные игры двух команд: **46 игр с 24.01.2025 по 19.12.2025, 806 участий, 552 голевых события**. Все они получают явную метку `2024-2025`. **13 турнирных листов пропускаются**: 03.11, 10.11, 17.11, 24.11, 01.12, 08.12, 14.12, 22.12, 29.12, 12.01, 18.01, 14.02, 23.02. Поэтому обычных игр с фактической датой 2024 года в этом импорте нет.

Карта [historical_import_2024_2025.json](../data/historical_import_2024_2025.json) содержит все подтверждённые полные даты, исключения и соответствия. Старый формат отличается от 2026: белые — M3:M10, чёрные — P3:P10, вратари — M11/P11; итог белых — E2, чёрных — C2. Голы белых — F/G при росте E, чёрных — A/B при росте C со строки 3. Пустая строка состава не заменяется вымышленным игроком. Суффикс «ВР» означает амплуа конкретного матча, отдельная личность не создаётся.

Подтверждены соответствия: Рус → Рус не придет, Кам → Камиль (уже связанная карточка), Виталя → Виталя пьяный; Серега/Антон/Айнур/Нави/Шаварш/Гриша/Аскар/Паша/Андрюша с «ВР» → одноимённый игрок; Филипп ВР → Фил, Влад ВР → Влад Татарбол, Старый Дубр → Дубр. Албанец, Миша Немец, Ринат от Вовы и Максим татарбол заводятся как новые игроки, по прямому уточнению владельца. Для ранее неизвестных Азата, Равиля, Тимофея и Сафонова суффикс роли не включается в alias.

Десять исходных передач к автоголам сохраняются в аудите без начисления ассиста — согласно правилам модели результата. Автор автогола, не указанный в источнике, остаётся неизвестным. Все 552 гола участвуют в счёте; автоголы не увеличивают личный зачёт голов. Исходные ячейки A:G и M/P до строки 51, номера строк, написания и SHA сохраняются в `history.imported` вместе с меткой сезона.

Порядок после миграции и резервной копии:

```sh
uv run python scripts/import_history.py --xlsx .local/history-previous-season-2026-10-18.xlsx --corrections data/historical_import_2024_2025.json
# После проверки на восстановленной копии, с FCZHK_DATABASE_URL нужной базы:
uv run python scripts/import_history.py --xlsx .local/history-previous-season-2026-10-18.xlsx --corrections data/historical_import_2024_2025.json --apply
```

Импорт атомарный, сериализован с оценками и связью профилей. Нерешённые замечания, неоднозначная карточка, повтор игрока после разрешения связей или существующая дата откатывают всю транзакцию. Повторный запуск не добавляет дублей. Новые неподтверждённые датированные листы или изменившийся формат исключённого турнира блокируют разбор. Импорт не создаёт заявок, оплат и заданий публикации; старые матчи и их ID не переписывает.

В интерфейсе «Период статистики» переключает общую историю и сезоны в архиве, личных показателях, партнёрах и зачётах; тот же выбор применяется к зачёту пользовательских прогнозов. OpenSkill всегда накапливается по всем завершённым играм в хронологическом порядке, без сезонных вариантов и сбросов. Все игры, существовавшие до миграции, получают сезон `2026`. Оценки сообщества остаются общими, без ретроспективного сезонного снимка. Выбор периода не меняет OpenSkill, команды и снимки уже утверждённых игр.
