# Выпуск и эксплуатация FCZHK

Актуализировано 20.10.2026. [Оглавление](README.md) · [Все переменные и CLI](CONFIGURATION.md) · [Проверки выпуска](TESTING.md). CI собирает и публикует образ; обновление сервера запускается оператором. Production-пилот и внешняя инфраструктура не считаются выполненными этой инструкцией.

Один Linux-сервер: Caddy → API, PostgreSQL и отдельный worker. Telegram доставляет обновления в API через webhook. Polling одновременно с webhook не запускается. Все процессы приложения используют один проверенный образ. CI собирает его один раз, проверяет миграции, HTTP, полный restore и SIGTERM, затем публикует в GHCR с полным Git SHA. На сервере сборка не выполняется.

## Подготовка

Нужны Docker Engine с Compose v2, Bash, util-linux (flock), coreutils, SSH и rsync. CI выпускает linux/amd64; для ARM нужен отдельный проверенный сборочный job. Клонировать соответствующую ревизию репозитория в /opt/fczhk: скрипты и compose.yaml должны соответствовать образу. Доступ к Docker равнозначен доступу администратора сервера.

1. Настроить домен, DNS и входящие 80/443. Порт БД 55432 привязан только к loopback; API 8000 наружу не опубликован.
2. Заполнить .env по [.env.example](../.env.example), права 0600. FCZHK_DATABASE_URL внутри Compose использует db:5432. Пароль в URL кодируется, POSTGRES_PASSWORD содержит его исходное значение. Изменение .env не меняет пароль уже созданной БД.
3. Создать бота, добавить его администратором сообщества, разрешить отправку и редактирование постов в чате публикаций. Задать FCZHK_BOT_TOKEN, FCZHK_BOT_USERNAME, оба chat ID, FCZHK_OWNER_ID, PUBLIC_URL и WEBHOOK_SECRET. Обычных администраторов владелец назначает в приложении; новый FCZHK_ADMIN_IDS оставить пустым.
4. Для входа из браузера задать Client ID и Trusted Origins в BotFather, как описано в [README](../README.md#вход-на-сайт-через-telegram).
5. Для приватного GHCR выполнить docker login ghcr.io учётной записью с правом чтения пакета. Токен не передавать аргументом командной строки.
6. На сервере доступны только администраторы и доверенные контейнеры: Compose доверяет forwarded-заголовкам внутреннего Caddy. При публикации порта API или изменении сети ограничить FCZHK_FORWARDED_ALLOW_IPS конкретными адресами прокси. Лимит входа действует на один API-процесс (30/IP и 300 суммарно в минуту); при нескольких экземплярах нужен общий лимитер.

## Первый запуск и обновление

### Если порт 443 занят другим сервисом

Для совместного размещения, например с VPN, предусмотрен вариант HTTPS на 8443. Он требует Compose 2.24.4 или новее. Compose можно установить отдельным CLI-плагином без переустановки или перезапуска Docker Engine. Работающие контейнеры и глобальную конфигурацию Docker при подготовке файлов не менять.

В `.env` задать:

```dotenv
COMPOSE_FILE=compose.yaml:deploy/compose.8443.yaml
DOMAIN=football.example.com
FCZHK_PUBLIC_URL=https://football.example.com:8443
```

`DOMAIN` содержит только реальное имя домена. В панели DNS направить A/AAAA на адреса этого сервера, разрешить входящие TCP 80/8443 в сетевом экране провайдера, сохранив существующие правила. Порт 80 используется для HTTP-01 проверки сертификата и перенаправления посетителей на HTTPS 8443. В этом варианте TLS-ALPN-проверка на 443 отключена. Указать полный адрес с `:8443` в Main Mini App, Trusted Origins и `FCZHK_PUBLIC_URL`; webhook использует тот же адрес. Telegram поддерживает webhook на 8443.

`deploy/compose.8443.yaml` полностью заменяет список опубликованных портов, а не добавляет 8443 к 443. Он также выбирает отдельный Caddyfile; обычная конфигурация 80/443 остаётся доступна без override.

Проверка конфигурации без запуска сервисов:

```sh
cd /opt/fczhk
docker compose --env-file .env config --quiet
docker compose --env-file .env config --format json | python3 -c \
  'import json,sys; print(json.dumps(json.load(sys.stdin)["services"]["proxy"]["ports"], indent=2))'
```

В выводе должны быть только 80 и 8443; команда показывает лишь порты, без значений секретов из окружения. Эта проверка не запускает контейнеры, не открывает порты и не выпускает сертификат.

Если на сервере запрещена остановка любых контейнеров, не запускать приведённый ниже `deploy.sh`: он останавливает сервисы FCZHK перед миграциями и при ошибке. Для первого запуска при таком ограничении нужен отдельный порядок: БД → миграции → импорт → первый запуск API/worker/proxy. До него проверить лимиты ресурсов, резервные копии и отсутствие пересечения сетей с VPN.

При проверке текущей сборки на сервере с 2 ГБ RAM использованы лимиты: PostgreSQL 384 MiB, API 384 MiB, worker 384 MiB, Caddy 96 MiB и служебный `tools` 384 MiB. Лимит worker 192 MiB приводил к OOM при одновременной работе процесса и проверки здоровья. Эти лимиты задаются отдельным серверным Compose override; расход памяти и счётчики перезапусков проверять после запуска. Лимит существующего контейнера можно увеличить через `docker update` без перезапуска, одновременно сохранив значение в override для следующих запусков.

### Переход с 8443 на 443

Для HTTPS порт 443 стандартный: посетители открывают `https://football.example.com` без порта. Перед переносом проверить и контейнеры, и слушающие TCP-сокеты: удаления прежнего контейнера недостаточно, если 443 занят другим процессом. Домен и DNS при сохранении того же сервера менять не требуется. Сертификат выдан на домен и подходит для обоих портов.

Обновить `FCZHK_PUBLIC_URL` на адрес без `:8443`. Проверить итоговые публикации портов в Compose с учётом всех override: основной HTTPS должен слушать 443, API остаётся внутри Docker. Изменение `.env` само по себе не меняет настройки работающих процессов. Новый API должен использовать новый публичный адрес, иначе проверка Origin отклонит браузерный вход. При обычном обслуживании настройки применяются пересозданием соответствующих сервисов.

Если остановка любых существующих контейнеров запрещена, перенос выполняется отдельно от `deploy.sh`: запустить дополнительный API и дополнительный Caddy на свободном 443 через `up --no-deps --no-recreate`, затем проверить HTTPS и readiness. Прежний Caddy на 80/8443 переключить через `caddy reload` на перенаправления 308 к адресу без порта с сохранением пути и query. До обновления webhook его старый путь можно проксировать в новый API. Новый Caddy должен использовать постоянное хранилище сертификатов; при совместном хранилище экземпляры [согласуют управление сертификатами](https://caddyserver.com/docs/automatic-https#storage). Если новый Caddy публикует только 443, для него использовать TLS-ALPN-01, а не HTTP-01 на занятом прежним Caddy порту 80.

Такой перенос требует дополнительной RAM и сохраняет прежние экземпляры API. Перед запуском проверить запас памяти; после — здоровье новых сервисов и неизменность ID, StartedAt, RestartCount и портов всех ранее работавших контейнеров. Старые экземпляры удаляются только в отдельно разрешённое окно. Зафиксировать имена активных сервисов и конфигурацию на сервере: стандартный `deploy.sh` не учитывает такой индивидуальный порядок переключения. Если worker оставлен со старым окружением, автоматическое расписание не включать до его обновления.

В BotFather добавить адрес без порта в **Trusted Origins**, обновить **Main Mini App**. После проверки HTTPS выполнить `configure-bot` и `check-bot` через отдельный `tools`: эти команды обновляют и проверяют webhook и меню бота, но не настройки BotFather. Проверить новый адрес в браузере, запрос challenge с новым Origin и реальный вход через Telegram. Старые HTTP- и HTTPS-ссылки должны приводить на новый адрес без предупреждения о сертификате.

### Обычный выпуск с окном обслуживания

Вставить полный SHA из успешного GitHub Actions либо digest из registry. Тег latest не используется:

```sh
cd /opt/fczhk
bash scripts/deploy.sh ghcr.io/OWNER/REPOSITORY:FULL_40_CHARACTER_GIT_SHA
bash scripts/compose.sh ps
```

Скрипт проверяет настройки, загружает образ, поднимает БД, останавливает API/worker/polling, сохраняет и полностью восстанавливает пробную копию существующей БД в изолированном контейнере, выполняет отдельный migrate и запускает API/worker/Caddy. Проверяет readiness и только после успеха сохраняет разрешённый digest образа в .local/release-image. Одновременные запуски deploy/backup-offsite/rollback блокируются flock. Обновление предполагает короткое окно недоступности; zero-downtime здесь не заявлен.

Ошибки не скрываются автоматическим откатом схемы. При ошибке миграции или readiness скрипт останавливает процессы записи; последняя попытка записана в .local/attempted-image, последний успешный выпуск — в .local/release-image. Если остановка тоже не удалась, проверить контейнеры вручную до восстановления. Ручные административные импорты на время выпуска запрещены.

База первого запуска пустая, резервировать её до начальной миграции не требуется. Шаблон автоматических игр по умолчанию выключен. Вручную собранный локальный образ проверяется без registry так:

```sh
docker build -t fczhk:local .
bash scripts/smoke-image.sh fczhk:local
```

## Импорт истории и оценок

Импортёры и карты соответствия включены в образ. XLSX монтируются read-only; .local/demo.db в production не переносится. Импорт выполнять в окно обслуживания, сначала dry run, затем запись. Перед импортом в непустую БД разобрать совпадения имён и карточек; автоматическое совпадение alias не доказывает личность. Импорт истории применяет явную карту `aliases`, повторно использует точный alias и подтверждённые связи карточек, в том числе из аудита. При неоднозначности запись блокируется; сходство имён не подтверждает личность. Не продолжать импорт только потому, что dry run успешно разобрал XLSX.

Образ работает от пользователя `app`, поэтому root-only файлы с правами 0600 в каталоге 0700 он прочитать не сможет. Узнать UID/GID можно командой `bash scripts/compose.sh run --rm --no-deps tools id`; группе приложения дать чтение XLSX и доступ к каталогу, например root-владелец, группа с GID из образа, права 0640 для файлов и 0750 для каталога. Монтирование оставить read-only, доступ остальным пользователям не открывать.

```sh
bash scripts/compose.sh --profile polling stop app worker bot
bash scripts/backup.sh /var/backups/fczhk
bash scripts/verify-backup.sh /var/backups/fczhk/ACTUAL_BACKUP.dump
bash scripts/compose.sh run --rm -v /srv/fczhk-imports:/imports:ro tools \
  python scripts/import_history.py --xlsx /imports/history.xlsx
bash scripts/compose.sh run --rm -v /srv/fczhk-imports:/imports:ro tools \
  python scripts/import_community_ratings.py --xlsx /imports/ratings.xlsx
# После проверки вывода повторить команды с --apply, в том же порядке.
bash scripts/compose.sh up -d --wait --no-deps app worker
# Если до обслуживания использовался polling:
# bash scripts/compose.sh --profile polling up -d --no-deps bot
```

Для актуальных выгрузок от 17.10.2026 ожидаются 19 исторических игр, 73 карточки после обоих импортов и 563 импортированных голоса. У первоначальных выгрузок 26.09 были 17 игр, 70 карточек и 589 голосов. Эти значения относятся к тем выгрузкам, а не к произвольному новому XLSX. Сверить SHA исходников, несколько протоколов и контрольные количества. Подробности: [история](HISTORICAL_RESULTS_IMPORT.md), [оценки](COMMUNITY_RATINGS_IMPORT.md).

Пользователь выбирает свою историческую карточку в профиле. Администратор проверяет соответствие и подтверждает в настройках. Конкурирующие заявки на ту же карточку отклоняются. История сохраняет исходные ID; чтение разрешает связь. Совместное участие двух карточек в одной игре блокирует слияние до исправления протокола.

## Telegram и пилот

```sh
bash scripts/compose.sh run --rm --no-deps tools fczhk configure-bot
bash scripts/compose.sh run --rm --no-deps tools fczhk check-bot
```

Первая команда меняет настройки бота и webhook; запускать после настройки HTTPS. Вторая только читает состояние webhook, сообщает число ожидающих обновлений и время ошибки, возвращает ненулевой код при неверном URL или ошибке за последние пять минут. Она не выводит токен, URL webhook или необработанный текст ошибки Telegram.

Обе команды выполняются в отдельном временном `tools`, чтобы не расходовать память работающего API вторым Python-процессом. Запуск через `exec app` при лимите API 384 MiB приводил к OOM и автоматическому перезапуску API. `--no-deps` сохраняет состояние зависимых сервисов; сами API и worker перед настройкой уже должны быть готовы.

Проверить реальными аккаунтами: вход участника/администратора, отказ постороннему, совпадение профиля при входе в браузере и Mini App, iOS/Android, запись, оплату, команды, прогноз и публикацию. Проверить пометку устаревшего поста. Отмена будущей игры сохраняет регистрации и оплаты, закрывает прогнозы и ставит уведомление в очередь. Отмена неопубликованного черновика не отправляет сообщение. Для пропуска ещё не созданной игры по дате есть исключения расписания.

Включать еженедельный шаблон только после пилота и проверки доставки, восстановления и уведомлений мониторинга.

При выпуске уведомлений `auction_start` обновить worker до переключения API: для упоминания капитанов он должен отправлять этот вид сообщений в HTML. Старый worker отправит HTML обычным текстом. Публикации `result` остаются текстовыми; новый worker также учитывает emoji при разбиении длинных итогов и помечает исправленные результаты. Миграция схемы для этих публикаций и сохранения силы сбора в существующем рейтинговом снимке не требуется.

## Резервные копии вне сервера

Операционные цели: RPO до 24 часов при ежедневной успешной копии; целевой RTO 60 минут. Это цели, которые нужно подтвердить замером на рабочем объёме данных и с реального внешнего хранилища. До настройки хранилища и таймера эти гарантии не действуют.

```sh
bash scripts/backup.sh /var/backups/fczhk
bash scripts/verify-backup.sh /var/backups/fczhk/ACTUAL_BACKUP.dump
```

backup.sh пишет новый файл через .partial, проверяет оглавление и создаёт SHA-256. verify-backup.sh проверяет checksum и полностью восстанавливает архив в новом PostgreSQL-контейнере без сети, выводит ревизию схемы и контрольные количества, удаляет только собственный временный контейнер. Для тестового restore нужен запас RAM: его data directory находится в tmpfs. Проверка не изменяет рабочую БД.

Готовность PostgreSQL проверяется по TCP на loopback контейнера, чтобы не принять временный сервер инициализации за рабочий. Restore и smoke ожидают до 60 проверок с интервалом 1 секунда; если сервер не готов, скрипт завершится с ошибкой до восстановления или миграций. Такое же TCP-условие используется healthcheck Compose и PostgreSQL-сервисом CI.

Настроить SSH-ключ с ограниченным доступом к независимому хосту, заранее проверить host key и создать каталог назначения. В /etc/fczhk-backup.env (0600):

```ini
BACKUP_DIRECTORY=/var/backups/fczhk
BACKUP_REMOTE=backup@backup.example.com:/srv/backups/fczhk
```

```sh
sudo install -m 0644 deploy/fczhk-backup.service deploy/fczhk-backup.timer \
  deploy/fczhk-backup-failure.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl start fczhk-backup.service
sudo journalctl -u fczhk-backup.service --no-pager
sudo systemctl enable --now fczhk-backup.timer
```

Ежедневно в 03:00 UTC выполняются dump → полный restore → rsync через SSH. Файл .local/last-offsite-backup обновляется только после успеха. Ошибка поднимает systemd failure и запись daemon.crit: подключить сбор этих событий к своему каналу оповещений; сам logger не отправляет внешние сообщения. Настроить внешний контроль возраста последней копии (порог 26 часов), свободного места и независимую retention-политику на хранилище. Автоматического удаления архивов здесь нет. Минимум раз в месяц скачать архив с внешнего хоста на другой сервер и повторить verify-backup, замерив время.

## Мониторинг

- /api/health: процесс API и доступность БД; используется Docker healthcheck.
- /api/health/ready: свежий успешный heartbeat worker, очередь и проблемные публикации. HTTP 503 требует проверки; Docker сам по себе не перезапускает unhealthy-контейнер.
- /api/metrics: Prometheus, доступ с отдельным FCZHK_METRICS_TOKEN; пустой токен отключает endpoint.
- Настройки → «Доставка сообщений»: задержка очереди, ошибки, неопределённые доставки и повторная пометка устаревших постов.

Готовые [настройки scrape](../deploy/prometheus.yml.example) и [правила тревог](../deploy/prometheus-rules.yml) покрывают недоступность API, остановку worker, очередь старше пяти минут, failed/uncertain, ошибки пометки и HTTP/webhook 5xx. Задать домен, файл токена, Alertmanager и реального получателя; проверить тестовой тревогой. Счётчики ошибок обнуляются при перезапуске процесса, поэтому правила используют increase. Проверку check-bot выполнять внешним мониторингом раз в минуту: HTTP-метрики не видят обновления, которые Telegram вообще не доставил.

При uncertain сначала проверить чат: повтор мог бы продублировать доставленный пост. UI требует явного подтверждения повтора. При failed проверить права бота и chat ID. При ошибке пометки устранить причину и нажать «Повторить пометку».

## Откат и восстановление

Для выпуска без изменения ревизии схемы:

```sh
bash scripts/rollback.sh
```

Скрипт использует сохранённый previous-image, проверяет предыдущую ревизию БД, останавливает процессы записи, запускает старый образ без миграций и проверяет readiness. При изменившейся схеме он откажется продолжать. Это намеренное ограничение: старый код нельзя автоматически запускать поверх произвольной новой схемы.

Если миграция или данные требуют восстановления:

1. Остановить app, worker, bot. Сохранить дополнительный дамп текущего состояния для расследования. Зафиксировать время и возможные записи после исходной копии.
2. Проверить checksum нужного pre-release-backup и выполнить verify-backup.sh. Выбрать копию совместимой ревизии, сохранить current DB без изменений.
3. Создать новую БД с уникальным именем и восстановить туда архив (пример имени заменять при каждом восстановлении):

```sh
bash scripts/compose.sh exec db createdb -U fczhk fczhk_recovery_20261017
bash scripts/compose.sh exec -T db pg_restore -U fczhk -d fczhk_recovery_20261017 \
  --no-owner --no-acl --exit-on-error < /var/backups/fczhk/ACTUAL_BACKUP.dump
bash scripts/compose.sh exec db psql -U fczhk -d fczhk_recovery_20261017 -v ON_ERROR_STOP=1 -c \
  "DELETE FROM login_sessions; UPDATE game_template SET enabled=false; UPDATE publications SET status='uncertain', error='После восстановления проверьте чат перед повтором' WHERE status IN ('pending','sending');"
```

4. Сверить alembic_version и контрольные количества с копией, проверить несколько матчей и оплат. Обновить имя БД в FCZHK_DATABASE_URL файла .env; записать соответствующий образ в .local/release-image. Для отката использовать checkout скриптов той версии. Поднять app/worker/proxy с --no-deps без запуска migrate. Старую БД не удалять.
5. Проверить вход, /api/health, heartbeat, протоколы и оплаты. Readiness может оставаться degraded из-за публикаций uncertain: сверить их с Telegram и вручную решить, какие повторять. Иначе после восстановления возможны дубли внешних сообщений.
6. Согласовать потерянные после копии изменения, возобновить расписание, проверить offsite backup. Зафиксировать фактические RPO/RTO и причину инцидента.

Команды восстановления намеренно не перезаписывают рабочую БД и не выполняют alembic downgrade с потерей новых данных.

## Схема и совместимость

Предыдущая миграция `e6b2f48a913c`: настраиваемые день и время открытия сбора и день игры. Миграция добавляет `opening_weekday=1`, `opening_time=12:00`, `game_weekday=4`, сохраняет прежние `start_time`, включение расписания, версии и существующие матчи. Время игры остаётся в `start_time`. Перед запуском нового API и worker применить миграцию; состояние переключателя не менять. Новые поля доступны в приложении без изменения `.env`. Downgrade откажется терять расписание, отличающееся от вторника 12:00 → пятницы. Обычный rollback между разными ревизиями схемы по-прежнему запрещён: проверять совместимость отдельно.

Предыдущая `a71f4b6d2e90` добавила поля решения владельца об административных правах и ревизию изменения. Миграция сохраняет существующих игроков; старый список продолжает работать до явного назначения/отзыва, а первый ID становится владельцем при отсутствии `FCZHK_OWNER_ID`. До обновления выбрать владельца явно. Назначения не требуют перезапуска; изменение самого владельца в окружении требует нового запуска процессов. Downgrade этой миграции откажется терять хотя бы одно решение владельца, включая отзыв прав.

Предыдущая `9c2d8f4a10b7` добавила уникальный индекс имени игрока и автоголы без известного автора; `8b1d6a0c42ef` — heartbeat worker, исключения расписания, заявки на связь профиля и индекс истечения сессий. Повторяющиеся имена останавливают миграцию до изменений; оператор должен проверить каждую карточку. Миграции не объединяют и не удаляют игроков. Downgrade также откажется работать при автоголах без автора, чтобы сохранить данные. `fczhk migrate` последовательно применяет отсутствующие ревизии. Демо-режим создания таблиц не заменяет миграцию существующих колонок и индексов.

`GET /api/matches` теперь возвращает краткие карточки страницами; внешним клиентам для полных данных нужен `/api/matches/{match_id}`. Остальные особенности совместимости описаны в [API](API.md). Перед обновлением checkout скриптов должен соответствовать выбранному SHA образа; после него зафиксировать SHA/digest, ревизию БД и расположение проверенной копии.


Предыдущая вершина Alembic — `f97c3e8d210a`: индексированная обязательная метка `matches.season`, всем существующим играм присваивается `2026`. Другие данные матчей и настройки расписания сохраняются. Downgrade отказывается удалять сезонность при наличии матчей с меткой, отличной от `2026`. До запуска API/worker применить миграцию, затем отдельным импортом добавить старые игры с картой `data/historical_import_2024_2025.json`; XLSX монтировать read-only. Сначала выполнить полный restore свежего backup, миграцию и импорт на изолированной копии рабочей базы. Проверить сохранение прежних ID, 46 новых игр, 806 участий, 552 гола и отсутствие новых заданий Telegram. Подробности — [журнал импорта](HISTORICAL_RESULTS_IMPORT.md#сезон-20242025-и-общая-статистика). Сервисы VPN, БД, proxy и Docker daemon для такого обновления не перезапускаются.

Перед выпуском — свежий backup и проверка восстановления с миграцией на изолированной копии. Основной канал публикаций остаётся в `.env`, а новые чаты задаются в админке. Переключатели аукциона, записей и отмен работают независимо и проверяются также перед отправкой очереди.

Для обратного отсчёта клиент получает серверное время через `GET /api/schedule/next`, обновляет цифры локально и синхронизируется каждые 30 секунд. На нуле он обновляет игру раз в 3 секунды до обработки расписания; разрешение записи остаётся серверным. Не отправлять просроченный анонс после открытия и напоминание после начала/отмены игры.
